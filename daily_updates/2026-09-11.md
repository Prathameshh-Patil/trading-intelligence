## 2. What was measured, and the controls that make it a finding rather than a guess


Then the same URL under widening conditions, to separate "our client is wrong" from "we are
blocked":

| | |
| :--- | :--- |
| `UA` + `Accept` (what the module sends) | timeout |
| full browser headers — `Accept-Language`, `Referer`, `Origin` | connection reset |

And the controls, same second: **`example.com` 200** and **`www.dukascopy.com` 200**. The network

**So this is not the `User-Agent` problem `SPOT_FEED_CHECK.md` §2 diagnosed, and not the missing
`Accept` header fixed in `6358d85`.** Both of those were client bugs with a clean fix. This is an
IP-level block on the data endpoint, tripped by roughly 40–60 requests in one evening, and it

**No further pulling.** Two probe rounds and one control round, spaced, then stopped. Grinding an
endpoint that is already refusing is how a block stops being temporary, and there is no result on

work and is not a decision for a session at 2am — it changes the question from "is this feed usable"
to "is this feed usable if we work around its limits", which is exactly the kind of thing the room
should answer with the vendor decision it already owns.

### S9 · The bars frame — ⏳ NOT FROZEN, and violated as written

S9 says a GC loader and a spot loader *"must produce the same frame, or the second instrument is not
a cross-check of the first"*, and that **"spot adds `bid`, `ask`"**. Measured, both loaders:

```
shared     close, high, low, open, session
GC only    cvd, delta, trades, volume
spot only  spread_bp, ticks            <- not bid, ask
```

Two corrections, and the second is the substantive one. `bid`/`ask` are tick-level and do not
survive bar aggregation — bars are built from the mid with `spread_bp` carried separately. And
**"the same frame" could never have held**: it is GC that carries the extra columns, because it has
a tape and spot does not, so the nullable-on-the-other-instrument columns are `delta`/`volume`/
`trades`/`cvd`, in the opposite direction to what S9 assumed. There is no arrangement where both
frames have the same columns short of inventing a `volume` for spot — the exact thing `has_flow`
exists to prevent.

**Proposed replacement, which the code already enforces:** a shared core of
`open/high/low/close/session` on a UTC index; each loader may add instrument-specific columns; and
**no portable feature may read outside the shared core** unless `has_flow` gates it. Checkable,
and satisfied today — which is why `atr_bp`, `session_phase` and `vol_state` run unchanged on both.
