## 1. Summary

**The Dukascopy block has changed shape, and the pull could never have converged even without it.**
Two separate facts, and the second is the one worth having:

1. The endpoint is **not** returning 503 to everything any more. Three cold probes returned real
   payloads — 49,523 and 104,222 bytes, plus a legitimate zero-byte Sunday hour.
2. **`spot.py` resumed by day, so a throttled pass discarded every hour it won.** With a request
   budget below 24 the loop cannot finish a single day however many times it is re-run. That is
   not slow; it is non-convergent, and it was invisible while the block returned 503 to everything.

The fix is four lines of moved logic and it is on `main`'s working tree, not committed —
`spot.py` now caches by hour. **No spot data has been pulled.** The budget is still far under a day.

**And the recovery measurement, which arrived late, is the one that decides it: the block has not
cleared in 13½ hours.** ~17 requests per budget against a recovery longer than half a day is
**~17 hour-files a day**; three months is 2,208 of them. **That is ~130 days, and it ends the
argument** — this address cannot bulk-pull this feed, and no amount of fixing `spot.py` changes it.

## 2. What was measured

Sequentially, from one address, over about 20 minutes:

```
3 cold probes, spaced          200, real payloads      49,523 / 104,222 / 0 bytes
pull, 2026-07-01               14 of 24 hours ok       10 LOST, day discarded, 519s
pull, 2026-07-02 00h           LOST
8 probes @ 6s pause            0 of 8                  after a 90s cooldown, 48s
```

**~17 successful requests from cold, then the wall**, and a 90-second cooldown does not lift it.
The failures after the wall are immediate rather than timeouts, which is what an IP-level refusal
looks like and not what congestion looks like.

**Then the recovery probe, and it is the decisive one:**

```
00:13  fail     00:18  fail     00:23  fail     02:26  fail
07:31  fail     09:05  fail     13:37  fail     13:53  fail  (confirming, separate)
```

**8 attempts across 13h 40m, every one refused.** ⚠️ **Read the spacing honestly: the probe was
written to fire every 5 minutes and the machine slept, so the intervals are uneven and the `t+N`
labels in its own output are wrong.** What the run supports is the span and the outcome, not a
cadence — and the span is what matters. This is consistent with 11 Sep's "22 hours was not enough".

**The arithmetic that ends it.** ~17 requests per budget, recovery longer than half a day, so call
it ~17 hour-files a day at best:

```
3 months    2,208 hour-files    ~130 days
19 months  13,896 hour-files    ~817 days
```

**A longer pause is not the lever.** 0 of 8 at a 6-second pause is worse than 14 of 24 at two
seconds, because the budget is consumed cumulatively rather than per unit time. `PAUSE` was raised
on 10 Sep on the theory that politeness buys throughput; against this budget it buys nothing.

**The zero-byte hour is not a failure.** 2026-05-10 is a Sunday — the market was shut, and
`fetch_hour` returning an empty frame there is the correct answer, which is why it is not counted
as a loss.

## 3. The defect the measurement exposed

`pull()` looped 24 hours into a list and wrote the day only if none was lost:

```python
if lost:
    continue          # the 14 hours that DID land are dropped on the floor
```

The resume granularity (a day) was coarser than the throttle budget (~17 requests). Every pass
therefore burned its whole budget, discarded the result, and left the next pass exactly where the
last one started. **Re-running it forever would have produced nothing**, which is a different
failure from "the pull is slow" and would have been read as the block never clearing.

**Fixed by caching each hour as it lands**, under `data/spot/XAUUSD/.hours/YYYY-MM-DD/HH.parquet`.
The invariant that motivated the day-level check is untouched: the day parquet is still written
only when all 24 hours are present, so **no day with holes ever reaches disk** and `atr_bp` /
`rv_slope` still cannot read an absent hour as a calm one. The hour cache is scratch and is deleted
once its day is assembled.

**Verification:**

- **2 new tests, 330 passing** (was 328), `ruff` and `mypy` clean.
- **The mutation fails.** Disabling the cache lookup (`if False and hf.exists()`) turns the new
  test red; reverting turns it green. The test asserts the second pass fetches *exactly* hours
  10–23 — the fourteen the first pass lost — and not the ten it already had.
- No test touches the network, per `test_spot.py`'s standing rule.
