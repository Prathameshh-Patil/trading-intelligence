## 3. The finding — the two axes deplete each other where they cross

The 28 cells below the floor are not scattered:

```
                  CONTRACTING  EXPANDING  STABLE
Asia-London                 8          0       2
London-NY                   8          2       2
NY                          0          4       0
NY-Asia                     0          2       0
```

**Both transition phases lose their entire CONTRACTING state — 8 of 8 each, 16 of the 28.**

The easy explanation is that those are the short phases. **That explanation is wrong, and the table
says so.** `vol_state`'s share of each phase's legs:

```
              CONTRACTING  EXPANDING  STABLE
Asia                0.282      0.275   0.443
Asia-London         0.100      0.427   0.473
London              0.201      0.198   0.601
London-NY           0.047      0.594   0.359
NY                  0.360      0.191   0.449
NY-Asia             0.322      0.132   0.546
```

CONTRACTING runs at 28–36% of the legs in the three phases that are not handoffs, and at **4.7%** in
`London-NY`. That phase is 08:00–09:30 ET, so it contains the 08:30 release: the hour before a
release is quiet, so the hour of it is EXPANDING almost by definition. **A handoff window is a place
where volatility is rising by construction.**

And the decisive check against the size explanation: **`London-NY` carries 14,652 legs to
`Asia-London`'s 9,768 — 50% more — and loses more cells.**

**This is the third route to the same artefact.** `M1_SURFACE.md` §3 found `London-NY` taking 73% of
the passing cells off 17% of the surface. `M3_CLOCK.md` §2 found its reach lift failing to convert
to EV. Both traced it to `atr_bp`'s trailing window sizing the bracket off the quiet hour before the
release. This is that fact seen from the volatility axis instead of the clock, and it is the first
time the two lanes' axes have been in the same table to show it.

**What is not being done about it.** No phase boundary moves, no `rv_slope` cut moves, no transition
phases merge. The surface has now been looked at, and `strategy-precommit.md`'s standing rule is that
a number changes only in a commit naming the measurement that moved it and never after the surface it
governs is visible. The dead cells stay dead and return `None`.

## 6. Why the slow build shipped first

**`first_touch` is essentially the whole 116 minutes, and the reason is measured:**

```
5,536 legs x 72 grid points x 2 tie modes = 797,184 leg iterations per (month, side)
6,968s / 38 month-sides / 797,184         = ~188 us per iteration
```

188 µs is pandas-per-row overhead, not arithmetic. Each pass rebuilds a `bars.loc[t:mark]` slice, a
session mask and two `.to_numpy()` calls, and `session_ends(bars)` is recomputed on every one of the
8,208 calls per month-side instead of once. The window depends only on `(t, side, horizon)` — not on
`target` or `stop` — so with three horizons and 144 calls per cell it is rebuilt 48 times to answer
48 questions reading the same two arrays. Hoisting it out of the grid loop turns the rest into numpy
over a ~5,500 × 12 array.

**Then fixed the same night — see §7.** The order was the point: the table was committed first so
that the faster version had something to reproduce.

**Also still open, and neither is mine to close:**

- **The two S7 seam mismatches.** `PipForecast.bucket` is `{regime, atrBucket, horizonBars, n}` —
  there is no `regime` in Track B (that is `regimes.py`, parked, and it does not port to spot) and no
  field for `phase`, `vol_state` or `instrument`; and `reach` is `{target, stop, p}[]`, which cannot

## 7. `first_touch` rewritten — 116 minutes to 3.4

Same night, once the table existed to check against.

**What was wrong.** `first_touch` was a Python `for` over every leg, and the window it slices —
`bars.loc[t:mark]`, a session mask, two `.to_numpy()` — depends only on `(t, side, horizon)`. The
barriers do not move it. With three horizons and 144 calls per cell (72 brackets × 2 tie modes) it
was rebuilt **48 times to answer 48 questions reading the same two arrays**, and `session_ends` was
recomputed on all 8,208 calls per month-side.

**The measurement that named it.** A 15-minute window costs the same as a 60-minute one:

```
horizon  15m :  1123 ms per call  ->  180 us per leg
horizon  30m :  1043 ms per call  ->  167 us per leg
horizon  60m :  1151 ms per call  ->  184 us per leg
```

A 3-bar window and a 12-bar window taking the same time means the arithmetic is free and the
slicing is all of it. That is what made the fix obvious rather than speculative.

**The shape.** `excursions(bars, trades, inst, horizon=)` returns the whole window as two
`(legs × bars)` arrays — favourable and adverse excursion in ticks, signed in the trade's own
favour so a long and a short read identically, padded with ∓∞ so a short window can never touch a
barrier. `first_touch_from(ex, target=, stop=, ties=)` answers one bracket off it in numpy.
`m1_sweep` builds the window three times per cell and answers all 144.

**`first_touch` keeps its signature, its docstring and its meaning**, and is now the single-bracket
spelling of `first_touch_from`. That was the constraint, not an afterthought: `bd675f5` is on the
record that a second first-touch convention is how two files quietly disagree about what a leg is
worth. There is still exactly one, and it moved rather than multiplied.

**Result.**

```
before   180 s per (month, side)     116 min
after      5.4 s per (month, side)     3.4 min      -- 34x
```

+93 / −28 lines across `backtest.py` and `m1_sweep.py`.

**Verification — reproduction, not "the tests pass".**

- **A cold-cache rebuild of all 19 months and both sides produces `reach_table.csv` byte for byte**
  — `cmp` clean, md5 `6711d1c7d0cab842cdcec486d0fed9ff` both sides.
- Four `(month, side)` checkpoints written by the *old* code compare equal frame-to-frame against

- 268 tests green, `ruff` and `mypy` clean across 51 files.

## Three bugs, none of which the typechecker could have caught

1. **`pnpm dev` was dead and had been.** `clickThrough.ts` calls `getCurrentWindow()` in three
   places; outside Tauri it **throws** rather than rejecting, so the existing `.catch` never fired
   and `SidePanel` failed to mount at all — blank page. Guarded with the official `isTauri()`.
   Found only by trying to look at the new view.
2. **The tie band was inverted.** `pMax = min(1 - pStop, ...)` clamped hardest exactly where
   `pStop` is largest — the tight corner — so `0.75/0.50` showed a narrower band than `0.75/1.00`,
   backwards from M1's finding that ties concentrate there. Moot now that the numbers are real, but
   the standalone check **passed the buggy version**: it compared only the two extreme corners and
   the inversion was local. The screenshot caught it.
3. **Rows came back in CSV order.** Arbitrary, and it broke the view's own stated invariant. Sorting
   by `p` would have been worse than arbitrary — whatever lands on top of a list reads as the
   recommendation, which is how a lookup quietly becomes a chooser. Now sorted by grid order,
   target then stop, with the check asserting it.
