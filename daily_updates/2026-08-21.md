## 3. Backend work (`services/api`)

### 3.1 Real analysis path — replaces the mock

**New file:** `app/analysis.py`

`POST /api/v1/analyze` previously returned a fixed `Bullish / 87.0 / …` response regardless
of input. It now runs a deterministic finance-word lexicon:

- Counts bullish and bearish terms in the selected text.
- **Negation handling** — a term preceded by a negator within three words flips polarity, so
  *"did not beat expectations"* reads bearish rather than bullish.
- **Confidence** is derived from how lopsided the hits are (margin) multiplied by how many
  there are at all (evidence). It never reaches 100, and returns exactly `50.0` when there is
  no usable signal.

No ML model and no network call, on purpose — plan §10 says do not chase the final model on
Day 1. The value delivered is a **stable contract** the extension can integrate against now.
Replacing the lexicon with a real model later only requires `analyze(text)` to keep returning
the same four keys.

### 3.2 Input validation and error handling

**Changed:** `app/api/routes/analyze.py`

| Field | Rule |
| :--- | :--- |
| `text` | Required. Whitespace-stripped first, then bounded to 1–20 000 characters. |
| `url` | Optional, ≤ 2 048 characters. |
| `title` | Optional, ≤ 512 characters. |

An empty or whitespace-only selection is now a clean `422` instead of an "analysis" of
nothing. `sentiment` is a `Literal` and `confidence` is bounded `0–100` on the response
model, so a future change cannot silently emit an off-contract value.

`url` and `title` are accepted and validated but do not yet influence the result. They are in
the contract from day one so the extension can send them without a later breaking change.

### 3.3 CORS

**Changed:** `app/main.py`

Allowed origins, by regex:

- `chrome-extension://<32-char id>` — the popup on Chrome
- `moz-extension://<uuid>` — the popup on Firefox (added in §7.2)
- `http://localhost:<port>`
- `http://127.0.0.1:<port>`

Methods `GET`/`POST`, header `Content-Type`, credentials not allowed (the API has no cookie
auth).

A regex is required rather than a fixed list because **the unpacked extension's ID changes
every time it is reloaded** in `chrome://extensions`. A hardcoded origin would have failed in
exactly the way plan §5 warns about: curl succeeds, the browser request fails.

### 3.4 Database health check

**Changed:** `app/api/routes/health.py`

`GET /api/v1/health/db` returned a 500 traceback when Postgres was unreachable. It now
returns `503` with a clean body:

```json
{"detail": {"status": "error", "database": "unreachable", "error": "…"}}
```

A health endpoint's job is to report "down" as a status, not to crash.

### 3.5 Tests

**New file:** `tests/test_api.py` — 15 tests, all at the HTTP boundary (request in, response
out; no testing of private helpers).

Covers: both health checks, all three sentiment outcomes, negation, response shape and types,
every validation rejection (missing / empty / whitespace-only / oversized / malformed JSON),

### 3.6 Interpreter pin

## 4. API contract (documented)

**New:** `services/api/README.md` — was empty, now holds the full contract.

Request:

```json
{ "text": "…", "url": "https://…", "title": "…" }
```

Response `200`:

```json
{
  "sentiment": "bullish",
  "confidence": 95.0,
  "summary": "5 bullish and 0 bearish terms across 14 words. Lexicon baseline, not a market forecast.",
  "signals": ["Bullish language: growth, record, strong, stronger, surged",
              "Confirm against price and volume before acting"]
}
```

Two points the client must not guess:

- **`sentiment` is lowercase** — `bullish` \| `bearish` \| `neutral`.
- **`confidence` is 0–100, a percentage — not 0–1.** Feed it to the confidence bar directly.

Errors: `422` for any invalid request body (standard FastAPI `{"detail": [...]}`); `503` from
`/api/v1/health/db` only, when Postgres is down. Clients should treat any non-200 as
"analysis unavailable" and show the `detail` text rather than retrying.

## 7. Extension build — was broken, now fixed

Found while verifying this update; fixed in the same session (`a8dea79`).

### The break

```
src/App.tsx(1,1): error TS1434: Unexpected keyword or identifier.
```

`apps/extension/src/App.tsx` contained a shell heredoc that had been **pasted into the file
instead of being executed**. It began:

```
cd ~/trading-intelligence/apps/web

cat > src/App.tsx <<'EOF'
import './App.css'
…
```

…and ended with a bare `EOF`. The file was 333 lines of valid React sandwiched between three
lines of shell. It came in with `36bcae4` and was already on `origin/main` before the backend
merge, so the backend work did not cause it.

Read the command's own first line — `cd apps/web`. The landing page had been written **for
`apps/web`** and landed in the extension by mistake, which is also why `apps/web/src/App.tsx`
was still the untouched Vite starter. One paste, two symptoms.

### The fix

1. **Landing page moved to where it belongs.** The 333-line component and its 433-line
   stylesheet were moved from `apps/extension/src/` to `apps/web/src/`, dropping the three
   shell lines. `apps/web` now serves the real Trading Intelligence landing page instead of
   the Vite starter — plan §3's first task, closed as a side effect.
2. **Extension popup written.** Its previous version (`85a14f7`) was also a Vite starter, so
   there was no popup to restore — it had to be written. The new `App.tsx` reads the
   selection from the active tab, shows it, and on **Analyze**
   POSTs to `/api/v1/analyze` and renders sentiment, a confidence bar, the summary and the
   signals. Loading, error and empty states are handled; `chrome.*` is guarded so `pnpm dev`
   still serves the popup as a plain page.
3. **`manifest.json` moved into `public/`.** The build succeeded but emitted a `dist/` with
   **no manifest**, which Chrome cannot load — exactly the "manifest/build mismatch" trap in
   plan §5. Vite only copies `public/`, so the manifest now ships with the bundle.

This also closes plan §3's "connect extension → API" item: the popup calls the real endpoint,
not a mock.

### 7.1 Match patterns — replaced with `activeTab` injection

`manifest.json` declared `content_scripts.matches` as `https://example.com/*` only, so the
content script never ran on a real news site and the §9 demo could not work.

Widening the list was the obvious fix, but `content_scripts` needs a **standing** grant on
every site it matches — with `<all_urls>` the extension would read every page you visit and
save every highlight to storage, forever, whether or not you use it. That is a lot of access
to buy a demo, and it is the kind of scope that draws scrutiny at Web Store review.

The extension now uses `activeTab` + `chrome.scripting` instead:

- The content script and its `chrome.storage` round-trip are gone.
- Opening the popup is the user gesture that activates `activeTab`; the popup then injects a
  one-line function that reads `window.getSelection()` from the active tab.
- Works on **every** site, and grants nothing persistent anywhere. Permissions dropped from
  `activeTab` + `storage` + a site match list to just `activeTab` + `scripting`.

This is exactly the §9 demo sequence — highlight, open Trading Intelligence, the text is
there — so the flow in plan §4 is unchanged from the user's point of view; only the mechanism
underneath differs.

Chrome refuses injection on `chrome://` pages, the Web Store and the PDF viewer. The popup
catches that and says so rather than showing an empty box.

### 7.2 Cross-browser (Chrome + Firefox)

The extension now loads in both browsers from the same `dist`. Three things had to change,
and the backend one is the least obvious:

1. **CORS — the real blocker.** The popup's origin is `chrome-extension://<32 chars>` on
   Chrome but `moz-extension://<uuid>` on Firefox. The regex in `app/main.py` only matched
   the Chrome form, so **every Firefox request would have been refused at preflight** no
   matter what the extension did. The UUID form is now allowed too; a malformed one is still
   rejected.
2. **API namespace.** Firefox's promise-based API is `browser`; its `chrome` shim is
   callback-based, so `await chrome.tabs.query(...)` would have resolved to `undefined` and
   thrown on the destructure — surfacing as the misleading "this page does not allow reading
   the selection" message. The popup now picks `browser ?? chrome` once, at the top.
3. **`browser_specific_settings.gecko`.** Firefox wants an add-on id; Chrome ignores the key.

The id is `{08df3b0c-6f2b-4eb3-a14b-e581e579d9e6}` — a generated GUID, which is one of the two
forms Firefox accepts and the one that needs no domain to own. It replaced a placeholder that
would not have survived an AMO submission.

**Treat it as permanent.** Firefox identifies the add-on by this string: change it after
publishing and users get a *different* add-on rather than an update, losing their settings and
their install. It should never be regenerated.

Firefox MV3 treats `host_permissions` as opt-in rather than granted at install, so Analyze
may need the localhost permission granted from the add-on's permissions panel. Noted in the
root README.

### 7.3 The demo, driven in a browser

Chrome automation became available late in the session, so the popup was exercised for real
rather than reasoned about.

`chrome://extensions` is off-limits to automation and "Load unpacked" opens a native file
picker, so the built popup was served with `vite preview` and given a stand-in for the
extension APIs — a fake selection. **The `fetch` to the API was not stubbed.** Everything from
React state down through CORS to the rendered result is therefore genuinely exercised; only
the `activeTab` injection is simulated.

| Step | Result |
| :--- | :--- |
| `apps/web` landing page | Renders the real Trading Intelligence page, not the Vite starter |
| Popup, selection present | Shows the text, the source title, Analyze enabled |
| Click Analyze | `bullish`, **95%**, confidence bar, summary and both signals rendered |
| Server side | `OPTIONS` 200 then `POST` 200 in the uvicorn log — a real request, from the browser |
| API stopped, click Analyze | Stale result cleared, error shown |
| API restarted, click Analyze | Result renders again, error cleared |

**A defect this caught.** With the API down the popup showed `Failed to fetch` — the raw
browser string, which tells a user nothing. `fetch` rejects with a `TypeError` when the host
is unreachable, and that is an `Error`, so the friendly fallback never ran. The unreachable
case is now separated from HTTP errors and reads: *"Cannot reach the API. Is the backend
running on localhost:8000?"* Re-verified in the browser after the fix.

This is exactly the kind of thing that survives unit tests and dies in front of a user, and it
would not have been found without driving the real UI.

### 7.4 The real thing, in a loaded extension

The extension was loaded unpacked in Chrome and the demo run for real: highlight a paragraph
on a page, click the toolbar icon, click Analyze. It returned **bearish** for the bearish
paragraph — the right answer for the text that was actually selected, not a stale or default
one.

Server side: **3 analyze POSTs, 0 preflights.** That zero is the interesting number. Every
request from the §7.3 harness preflighted, because `localhost:4173` is an ordinary web origin.
The extension's requests did not, because an extension holding `host_permissions` for the API
bypasses CORS entirely. So the two paths are distinguishable in the log, and the requests that
rendered the verdict provably came from the extension rather than from a page.

A consequence worth writing down: **the `chrome-extension://` CORS regex is not what makes
Chrome work.** `host_permissions` does. The regex still matters for Firefox and as a fallback
if those host permissions are ever narrowed, but it is not load-bearing for this path.

**Two defects found while getting here:**

1. **No icons at all.** The manifest declared neither a top-level `icons` key nor
   `action.default_icon`, so a loaded extension gets a blank grey placeholder in the toolbar —
   which is why it could not be found by eye. The brand mark in `public/favicon.svg` is now
   rasterised to PNG at 16/32/48/128; Chrome does not accept SVG for extension icons.
2. **The load had silently not happened.** "Load unpacked" only appears once Developer mode is
   on, so the first attempt produced no extension and no error. Worth knowing for whoever sets
   this up next.

### 7.5 `apps/extension/dist` is now committed

Loading an unpacked extension means pointing Chrome at a built folder, so a gitignored `dist`
meant anyone cloning the repo had to `pnpm install && pnpm build` before the extension existed
at all — and again after every pull, since Chrome keeps serving whatever bundle was on disk
when it was loaded. `apps/extension/dist` is therefore tracked: 10 files, 248K. `apps/web/dist`
stays ignored, because it is served rather than loaded by hand.

Un-ignoring it took edits in two files — the root `.gitignore` has `dist/` and
`apps/extension/.gitignore` had its own `dist`. Git cannot re-include a file whose parent
directory is excluded, so one negation alone would not have worked.

**The cost, stated plainly.** Committed build output can go stale: source changes, nobody
rebuilds, and the repo disagrees with the loaded extension. That is precisely the
"source correct, `dist` wrong" mismatch plan §5 lists as a likely conflict, and burying the
build output in git makes it quieter rather than less likely. The minified bundle and the icon
PNGs will also churn on every rebuild, so expect merge conflicts there — **resolve those by
rebuilding, never by merging.**

**The guard.** Vite hashes asset filenames, so any real source change shows up in `git status`
after a build. A clean `git status` following `pnpm build` therefore *is* the staleness check,
and it was verified: rebuilding after the commit left the tree clean, so the committed `dist`
is byte-identical to a fresh build. There is no CI to enforce this, so it lives in the README
and here. If CI ever appears, the one-line version is
`pnpm build && git diff --exit-code apps/extension/dist`.
