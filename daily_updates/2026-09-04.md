### The bug the tests caught, which is the reason to write tests first

The EMA gate originally compared `sign(close − ema)` against a **one-bar** slope. A test asserting a
falling market fails alignment blew up, and chasing it produced the actual result:

> `ema_t` always lies between `close_t` and `ema_t−1`. So `close > ema_t` and `ema_t > ema_t−1` are
> the *same statement*, and the two signs can never disagree.

The gate was a **tautology** — it would have passed every bar except an exactly flat one and filtered
nothing at all, while looking entirely reasonable in the pass-rate table. The slope is now measured
over `span` bars, where the two quantities are genuinely independent. The case it now rejects — price
rallying back above an average that is still below where it was — is a bounce inside a downtrend, and
there is a test pinning it.

Worth noting the failure mode: this would not have shown up as a crash, a type error or an
implausible number. It would have shown up as a filter that quietly did nothing.

## The regime plot, reviewed — and D1's gate was wrong

D1's `survival >= 0.92` was implemented as specified and flagged as "Varad's call, not a bug to patch."
That was the wrong place to stop: `regimes_2026-09-02`'s own README says the run is unreviewed, and the
gate was accepted anyway. Reviewed now, before D3 consumes it.

### What the plot shows

Regimes 0 (blue) and 1 (orange) never form contiguous blocks. They appear as speckle *inside* green
stretches, clustering on the steep CVD legs — 0 on rising CVD, 1 on falling. Green (regime 2) is
everywhere else and is most of the chart.

That picture is consistent with both readings — genuinely unstable states, or stable states that are
simply rarer — so the transition structure had to settle it.

### It settles decisively: they are stable, and the threshold was measuring prevalence

**Raw survival is confounded by base rate.** A regime occupying 63% of bars scores 0.63 by shuffling
alone; one occupying 15% scores 0.15. An absolute threshold on survival is therefore a threshold on
*how common a regime is*, wearing a different name.

Normalising — `kappa = (P(stay) − share) / (1 − share)`, Cohen's kappa against a shuffled-label null —
**inverts the ranking**:

| regime | share | P(stay) | vs chance | **kappa** | E[run] |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 0 | 15.4% | 0.866 | **5.61×** | **0.842** | 7.5 bars |
| 1 | 21.5% | 0.875 | **4.07×** | **0.833** | 8.0 bars |
| 2 | 63.0% | 0.927 | 1.47× | 0.798 | 13.7 bars |

**The transition matrix rules out instability.** `0→1 = 0.0043`, `1→0 = 0.0023`. The two flow regimes
essentially never alternate with each other; they decay into 2 (0.129, 0.122) and come back. The
churn-between-opposite-flows failure mode simply is not there.

**And they are not high-variance.** `price_efficiency` sd: **0.243 / 0.233 / 0.230** — identical.
`cvd_persistence` sd: 0.200 / 0.191 / 0.153. On the clustering's own features, 0 and 1 are no noisier
than 2.

Meanwhile **regime 2 is the residual bucket**: `cvd_persistence` 0.206 against 0.61,
`price_efficiency` 0.341 against 0.54, `cvd_slope` −0.199 with sd 11.4 — noise around zero. So the gate
kept the one state where nothing coherent is happening, and discarded both that carry flow, for a
strategy family built on flow.

### What changed

`regime_filter.py` gates on **kappa**, not raw survival. `regime_survival()` stays as the raw input and
a reportable diagnostic. **The 0.92 number is retired**, with the reasoning written into
`analysis/regimes_2026-09-02/README.md` where the labels live. Two new tests: one asserting kappa
reverses a raw-survival ranking that favours the common regime, one asserting a single-regime frame
gives NaN rather than dividing by zero. 99 tests green.

### D1's number changes, and the new one is worse

All three regimes clear `kappa >= 0.75` on the training half — 0.842, 0.833, 0.798. **So on this
labelling the regime dimension carries no filtering information at all.** That is the honest result: the
clustering separates *what the market is doing*, but not *whether the label will hold*.

| `atr_min` | bars | pct |
| ---: | ---: | ---: |
| 40 | 2,409 | **38.4%** |
| 45 | 1,879 | 29.9% |
| 48 | 1,573 | 25.1% |
| 50 | 1,407 | 22.4% |

**At the committed `atr_min = 40` the filter now passes 38.4%, above D1's 15–25% band.** The 19.9%
logged this morning is superseded — it was 19.9% only because the regime gate was silently doing the
work of excluding 37% of bars on a criterion that turns out to be prevalence.

**The filter is now three gates and ATR carries nearly all of it.** Reaching the band needs
`atr_min ≈ 50`, which is the tuning problem from D1 again, now with nothing sharing the load. Whether to
raise `atr_min`, accept 38.4% and report it, or find a fourth gate that is not ATR, is open — and it is
a threshold decision, so it is not one to take here.

## The fourth gate — `cvd_persistence`

The kappa correction left the filter with three live gates and ATR doing nearly all the work, which
re-opened the tuning problem with nothing sharing the load. The fix is a fourth gate on a **flow**
quantity, and the obvious candidate was already in the diagnosis: `cvd_persistence` is what separated
the flow regimes from the chop bucket in the first place (0.61 against 0.21).

### Where it lives, and why that changed `regimes.py`

`cvd_persistence` is `|Σδ| / Σ|δ|` over a trailing window — dimensionless in [0, 1], one meaning every
contract went the same way. It already existed as `regimes._cvd_persistence`, because the clustering
needed it before anything else did.

Two copies would let the regime labels and the gate that filters on them drift apart, so there is one.
But the direction of the import matters: **the function moved *out* of `regimes.py` into
`features/orderflow.py`**, and `regimes.py` imports it. It is a feature the clustering consumes, not a
detail of the clustering.

The practical reason is sharper than the aesthetic one: **importing `regimes` costs ~2.3 seconds**
because it pulls `sklearn`. Had `orderflow` imported *from* `regimes`, D3's engine would have paid that
on every run to reuse four lines of arithmetic. A test pins
`regimes._cvd_persistence is of._persistence` so the move cannot silently un-happen.

### It reproduces the labels' separation, computed from bars

The gate does not read the `cvd_persistence` column out of the labels CSV — it computes the feature
from bars, so **it does not depend on a labelling that is still unreviewed and unpromoted.**

That makes the agreement a real check rather than a tautology:

| regime | computed here (60min/6) | `regimes_2026-09-02` README |
| ---: | ---: | ---: |
| 0 | **0.612** | 0.612 |
| 1 | **0.613** | 0.6125 |
| 2 | **0.206** | 0.2059 |

A clock-based trailing window and `regimes.py`'s bar-based one agree to three decimals on this frame.

### D1's number, and `atr_min` stays where it was committed

| `persistence_min` | bars | pct |
| ---: | ---: | ---: |
| 0.00 | 2,409 | 38.4% |
| 0.20 | 1,691 | 26.9% |
| 0.30 | 1,358 | **21.6%** |
| 0.35 | 1,206 | **19.2%** |
| **0.40** | **1,043** | **16.6%** |
| 0.45 | 887 | 14.1% |

**1,043 of 6,276 bars — 16.6%, in band — at the committed `atr_min = 40`.** That is the structural
point: the band is reached without touching ATR, so the volatility floor is no longer the thing being
tuned to produce a target number.

**And 0.40 is not chosen because it lands in band.** The two populations sit at 0.206 and 0.612/0.613;
their midpoint is **0.409**. The threshold separates the two clusters the labelling already found, and
lands in band as a consequence. That is a materially better provenance than `atr_min = 40` has, and it
is the first threshold in this filter with an argument behind it that is not the pass rate.

### Still open, and it is two numbers now

`persistence_min` and `atr_min` are both thresholds chosen while looking at the month. The persistence
one has an independent justification; **`atr_min = 40` still does not**, and it is now the weakest link
in the filter's provenance. Both belong wherever the filter's thresholds get committed, on the same
terms as Part B — before anything is backtested through them.
