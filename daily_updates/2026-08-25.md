## What changed

### `app/analysis.py` — rewritten

The Day 1 lexicon is deleted. `analyze(text)` now makes one `client.messages.parse` call
to `claude-haiku-4-5` with a system prompt that defines each of the four fields, and
decodes the reply through a Pydantic `Analysis` model via structured outputs.

Structured outputs rather than forced tool use: same guarantee that the shape is
enforced, but no tool-call round trip and no manual `json.loads`, so it is meaningfully
less code for an identical result. `parsed_output` is `Analysis | None` — `None` means
the model refused or ran out of output tokens mid-object, so that raises rather than
returning a half-answer.

The four keys are unchanged. That was the whole design of the Day 1 baseline and it held:
no extension change, no contract change, no migration.

### `app/api/routes/analyze.py` — a `503` path

`anthropic.APIError` (service down, rate limit, bad key) and a schema-failing answer both
become `503 {"status": "error", "analysis": "unavailable", "error": "..."}`. This mirrors
the shape `/api/v1/health/db` already returns, so the API has one way of saying "the thing
behind me is not answering" rather than two.

`ValidationError` subclasses `ValueError`, so one `except (anthropic.APIError, ValueError)`
covers both. The function it wraps is five lines, so the catch is narrow in practice.

Checked the extension before adding this: `apps/extension/src/lib/api.ts` renders any
non-200 as `The analysis service returned ${status}` and never reads `detail`, so a
dict-shaped detail cannot break it. No extension change needed.

### `app/config.py`, `.env.example` (both) — the key

`anthropic_api_key: str`, required, no default — identical treatment to `database_url`.
A missing key is a startup failure with a clear pydantic error, not a surprise at the
first request. Documented in `services/api/.env.example` and the repo README, including
the point that tests only need the key to be *present*, not valid.

### `tests/test_api.py` — restructured

The old `test_bullish_text` / `test_bearish_text` / `test_neutral_text` /
`test_negation_flips_sentiment` asserted real lexicon behaviour. Against a network call
they would be slow, flaky and billable; against a stub they would be asserting that a stub
returns what the stub was given. Neither is worth having, so they were split:

- **13 boundary tests** stub `run_analysis` via `monkeypatch` and cover what actually
  breaks silently: response shape, whitespace stripping, the three validation rejections,
  the `503`, and CORS across Chrome/Firefox/localhost plus a foreign origin.
- **5 live tests** (bullish, bearish, neutral, negation, confidence/signal bounds) make
  real calls and skip unless `LIVE_API_TESTS=1`. A normal `uv run pytest` spends nothing.

Four more were added later in the day — see the verification section, which is where the
weakness in this split showed up: stubbing `run_analysis` meant `analysis.py` itself was
never executed by any test. Final count 17 (+5 skipped).

## Going back to verify — and the defect it caught

Went back to actually verify rather than trust the green suite, by driving `analyze()`
against a faked Anthropic transport (`httpx2.MockTransport`) so the real request building
and decoding ran. Four cases; two of them failed in a way that mattered.

**The defect.** `Analysis` was validating the *system prompt's style* as if it were the
contract: `confidence` bounded to 50–95, `signals` to at most 4. Dumping the schema the SDK
actually sends showed why that is wrong — numeric bounds and list maximums are stripped and
reappear only as a description string:

```
"confidence": {"type": "number", "description": "{maximum: 95, minimum: 50}"}
```

So the model is *asked* for 50–95, not constrained to it. And because `messages.parse`
validates client-side on the way back, any bound placed there becomes a hard error rather
than a correction. A model answering `confidence: 97` — a perfectly usable analysis —
raised `ValidationError`, which my own route then dutifully turned into a `503 analysis
unavailable`. Same for a 5th signal. Two spurious user-facing failure modes, both invented
by me, neither visible to `ruff`, `mypy`, or 13 passing tests.

Fixed by writing `Analysis` to the contract rather than the prompt: `confidence` 0–100,
`signals` non-empty. The prompt still asks for 50–95 and 1–4. Genuinely unusable output
(truncated JSON, refusal) still fails, which is correct.

| Model returns | Before | After |
| :--- | :--- | :--- |
| well-formed reply | 200 | 200 |
| `confidence: 97` | **503** | 200 |
| 6 signals | **503** | 200 |
| truncated JSON | 503 | 503 |

This is the second real defect verification caught, after the mypy `None` one. Both were in
code that type-checked and tested clean.

**The failure path is now verified against the real API.** A live call with the placeholder
key reached `api.anthropic.com` and came back `AuthenticationError` (401) — an `APIError`
subclass, so the route's `503` mapping is confirmed against the real service rather than a
mock of it. Costs nothing, since a rejected request is not billed.

## Later — the twelve-week execution path, split three ways

Source: the **Twelve Weeks to Ten Subscribers** artifact (shared, read 25 Aug). It says what to

**Two architectural facts from the artifact now constrain everything in this repo:**

- **A screenshot can never contain delta.** Delta needs the aggressor side of every individual
  trade; a rendered candle discarded that when it was drawn. Two sessions with identical candles
  can have opposite CVD. Capture stays, demoted to *context only* — symbol, timeframe, drawn levels.
  Every number comes from the feed. This is enforced as a type (`CaptureContext` carries no numeric
  field but `levels` and `confidence`) rather than as a convention, because it is exactly the
  mistake that becomes tempting in week eight.
- **Bring-your-own-feed.** The user connects their own CME entitlement, the overlay computes delta
  on their machine, no market data touches our servers. Databento's external distribution rights
  start at $1,750/mo, not the $199 tier; CME wants a separate five-figure derived-data licence on
  top. Deleting that one hop deletes the whole licensing bill. The cost is a narrower launch
  audience — futures traders on GC and NQ, not anyone with MT5.

web pages), with a deliberate frontend→backend ramp: Week 5 he consumes an API contract he did not

## Evening — the "own model" is not what the plan thought it was

Item #1 said *scope the own model and give it a week in `plans/team/`.* Scoping it revealed the row
was describing the wrong thing entirely.

**The first question was which of two jobs the model was for**, because the plan had been using one
phrase for both: text sentiment behind `/api/v1/analyze` (the extension popup, Day 1–3 work that no
week of the twelve-week plan actually ships), and the **vision** extraction behind S6

context, $20–50/mo"* line was budgeting for, and which `contracts.md:234` already warns about.

The answer was **neither.** It is a **GC strategy selector**: given the trader's own defined
strategies, the live order-flow state and journal history, choose which strategy fits this moment —
and say how many ticks it expects to be right by.

That reframing is worth more than the design that followed it. The row would otherwise have been
worked as "replace Claude", which is not the thing anyone wanted.

**It also has a home already.** `apps/extension/src/lib/types.ts` has carried `Strategy` (thesis,
`entryCriteria[]`, `exitCriteria[]`, `maxRiskPct`), `StrategyStats` (winRate, expectancy) and
`JournalEntry` (outcome, `rMultiple`) since Day 1, plus `StrategyReviewView` and
`StrategyChangeView`. The idea sits on top of things that already exist. `Strategy` has **zero
instances** anywhere, though — a selector with an empty candidate set is a regime classifier with
extra steps, so defining the candidates is the first real task and it belongs to the person who
trades them.

### The two flags raised before designing anything

Both get more expensive the later they surface, and both were put on the table before a line of
spec was written:

- **This crosses a regulatory line the rest of the product does not.** Flagging an outlier delta
  print is *information*; telling a trader which strategy to use is a *recommendation*. Shreyas's
  Week 1 Tuesday CA call already asks whether the product as described triggers SEBI Research
  Analyst registration — and the answer depends on which product is described.
- **Nothing can validate it yet.** The backtest harness is Week 4; journal outcomes need beta users
  in Week 7. Until then a strategy-chooser is unfalsifiable and will look excellent in every demo,
  which is the exact failure mode `varad/thresholds.md` exists to defend against.

**Resolved by scope, not by argument:** it is a **personal research tool for GC trading, not a
product feature.** That removes the SEBI exposure entirely and means it takes **no week** from

being scheduled — which is a better outcome than finding it a week.

### The design — A and C mixed, with the seam between them made explicit

Three approaches were weighed: rules-first (A), an LLM agent reading the state (B), and learning
regimes from the data (C). B was argued against on record — non-deterministic so it cannot be
backtested honestly, needs a GPU box which reintroduces the hosting cost, and its explanations are
persuasive whether or not they are correct.

The chosen shape mixes **A and C**, and the seam matters:

- **A defines the candidates and proves they are worth anything.** 3–4 hand-written GC strategies,
  each backtested standalone against a random-entry null. **This is a kill gate** — if none has a
  standalone edge, there is nothing to select between and the rest is moot, discovered in days.
- **C decides when to use which.** 2–3 regimes, clustered on *state* features only (realized vol,
  CVD slope, directional efficiency, session phase).

C earns its place for a specific reason: in a pure-A design each strategy declares its own regime
preconditions — *"this one works in trending flow"* — and **that assertion is itself an unvalidated
story.** Learning it is more honest. It is also more dangerous, hence the guardrails.

**The guardrail that matters most is the second null.** Beating "always use the single best
strategy" is table stakes. The real test is *does learned regime selection beat random regime
assignment with the same regime proportions* — that is what catches fitting noise, and Stage 2 lives
or dies by it. Alongside: regime definitions pre-committed to git before anyone looks at performance
inside them, walk-forward rather than in-sample, N reported next to every number, nothing acted on
below ~30 samples per cell.

**The predicted outcome is recorded in the spec, before the work:** with ~22 sessions split
walk-forward, the most likely honest result is **inconclusive**. Written down now so it cannot be
quietly reinterpreted later. The cheapest fix is more data, not more modelling — one GC month cost
$2.52, six months is roughly $15.

### Magnitude in ticks, and the error bar it inherits

Added at Varad's request: the selector has to say **how far**, not just which way. Every backtest
reports realized move at 5/15/30 min, **MFE and MAE**, and median/IQR/p10/p90 — *distribution, never
a point estimate*, because these are fat-tailed and a mean is a lie.

**Units pinned in the spec, deliberately.** GC is COMEX gold, 100 troy oz, min tick 0.10 = $10/contract;
a point is 1.00 = 10 ticks = $100. **"Pips" is FX/MT5 terminology and does not apply to GC futures.**
Pinned because this project has already lost a work item (A2) to spot-vs-futures confusion, and an
unstated unit is how the second one happens.

**And the error bar is inherited, not introduced.** §3 of the findings puts session-total delta at
~15–20% method-dependent. **Any strategy whose entry threshold is a delta magnitude inherits that
directly** — a rule firing at "delta > 200" fires somewhere between ~170 and ~240 depending on
classification method. Every headline result gets re-run with thresholds perturbed ±20%; an edge
that does not survive its own known error bar was never an edge.

### The decision filter — a seam left deliberately empty

Varad authors it, not Claude. Contract: a pure function over the selector's output that can **veto**
(returning `None` is a first-class outcome) and can **size**, but cannot change the strategy choice
or invent a signal. Every backtest reports pre-filter and post-filter numbers side by side, so it
stays visible whether the filter helped or merely shrank the sample until the numbers looked better.

```
compute_delta_cvd on the S1 fixture -> session delta: 0 | nonzero rows: 0
```

`np.select` with no matching condition returns its default, so every trade scored 0 delta and the
script printed a clean, plausible, entirely empty result. This is the same class of failure as the
`'N'` NaN — a mapping that does not cover its input, failing quietly. **The fixture is the file
every test in this project asserts against for the next twelve weeks**, and the project's main
analysis script could not read it.

Fixed by folding `compute_delta_cvd.py` onto `s1.py` rather than by patching the mapping in place:
its `load_trades`, `add_delta`, `session_cvd`, `minute_bars` and `SESSION_SHIFT` are deleted and
imported instead — **439 → 376 lines**, and one definition of what a session and a bar are, so the
script and the harness cannot drift apart.

**Proof the refactor changed nothing else:** re-ran the script end to end against the fixture and
diffed its footprint CSV against `analysis/gc_footprint_2026-07-16.csv`, which was committed
earlier from the *full month* through the *old* code. **980 levels, 980 common, `buy_vol`,
`sell_vol`, `total_vol` and `delta` identical at every one, max abs diff 0.** That also
re-confirms, from a third direction, that the fixture is the right session cut correctly.

### `backtest.py` — §4's metric set, and the trap it exists to avoid

108 lines. `evaluate` returns one row per entry; `summarize` returns the distribution for one
horizon; `report` stacks the horizons. Every summary carries `n` and a `thin` flag that fires
under 30 samples, which is §6.5's rule made mechanical rather than remembered.

Two decisions worth recording:

- **Horizons are measured on the clock, never on row offsets.** `minute_bars` drops minutes with
  no trades, so `bars.iloc[i + 5]` is not five minutes after `bars.iloc[i]` — on a quiet overnight
  hour it can be an hour later. Every window is a `.loc[t : t + Timedelta]` slice. There is a test
  that builds bars at minutes 0,1,2 then 10,11,12,13 where the row-offset answer and the clock
  answer differ by 100 points, and asserts the clock one.
- **No window crosses a session boundary.** A position held through the overnight break is a
  different trade than the one being tested, so the window is filtered to the entry's own session
  and an entry on a session's last bar is dropped rather than scored.

The fill assumption is stated once at the top of the file: an entry fills at the **close of the
bar that signalled it**, so a strategy reading its own bar's close is fine and reading anything
from the next bar is lookahead.

`random_entries` is §6.3's Stage 1 null — matched count, matched holding period, and **matched
side mix**, because a long-biased rule measured against a coin flip in a rising market beats it on
the drift alone and that is not an edge.

### A test corrected my own comment

I had written that MAE "stays signed negative". A test on a short that never traded against itself
returned **+10 ticks**, and it was right: MAE is the *least favourable* excursion, which is positive
when a trade never goes adverse. Flooring it at zero would have hidden exactly the trades that need
no stop. Comment fixed to match the behaviour, and the invariant asserted is now `mae <= mfe`.
